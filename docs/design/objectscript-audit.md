# ObjectScript repository audit

**Date:** 2026-10-15 · **Applies to:** `main` at `1346bbc` (release `setup-cli-v0.2.0`) · **IRIS used for checks:** `iris-demo`, IRIS 2025.3, namespace `OPCUA`

Items marked ✔ were checked against the running IRIS instance or confirmed in the
code by hand. Everything else comes from reading the code; "plausible" means likely
but not reproduced. No code was changed as part of this audit.

Items marked ✅ have since been fixed; each one notes the fix and how it was verified.

## Summary

The code is in better shape than most AI-generated ObjectScript. The classic syntax
traps are absent: no `$Get(obj.prop)`, no `Quit value` inside loops or Try blocks,
no bad postfix spacing, no transaction misuse.

The real problems are subtler. They are in error codes, edge cases around lists and
names, and how the code affects other things on the IRIS server (other productions,
leftover data).

## Should fix

5. ✅ ~~**One short result list kills a whole poll cycle**~~ **Fixed 2026-10-21** ✔ (`RowWriter.cls:173`). `$LI(pInput, i)` throws `<NULL VALUE>` when an element is missing. That device and every device after it lose that cycle. Use `$ListGet`. **Fix:** `BuildRow` now reads with `$ListGet`, so an empty slot stores NULL for that one column and the other columns and devices are still saved. A live poll of `plc` showed the native library keeps a slot for every node: a missing node comes back in place as a Bad reading with no value. Builds before `ca5bbbb` kept the slot too, with an empty value, and every shipped binary (Linux and Windows) includes that change. As a safety check, the new `RowWriter.CheckInput` compares the reading count with the device masks, and both row-source services refuse a cycle whose count is wrong with an error giving both counts. Readings are matched by position, so a list of the wrong length would otherwise store values under the wrong columns without any error. Added `MeasurementMetadataTest.TestShortInput` (an empty slot, then a short and an empty list): it failed on the old code with `<NULL VALUE>` and passes now. Also added `CheckInput` checks against a real poll and a real subscription notification. Verified on IRIS 2025.3: `OPCUA` and `Examples` compile clean. Against `plc`: `MeasurementMetadataTest` 219/0, `PortalPipelineTest` 38/0, `ResolverTest` 78/0.
6. ✅ ~~**The Projection reports the wrong error**~~ **Fixed 2026-10-21** ✔ (`Projection.cls:90`, `:167`). `ProcessObj` uses `cls`, a variable that only exists in another method, and never initialises `tSC`. A user who forgets `OPCUANAMESPACE` gets `<UNDEFINED> cls` instead of the helpful message. **Fix:** `ProcessObj` starts with `tSC = $$$OK`, and the message uses `oObj.Name`. The message also named the class default as `OPCUADEFAULTNAMESPACE`, but the real parameter is spelled `OPCUDEFAULTANAMESPACE` (declared in `Definition.cls` and used by every schema, so it was not renamed), and the message now says so. Added `MeasurementMetadataTest.TestProjectionErrors`. It failed on the old code with `<UNDEFINED> *cls`, and with `<UNDEFINED> *tSC` for a schema with no data columns, which was a second real crash. It passes now. Verified on IRIS 2025.3: `OPCUA` and `Examples` compile clean, and every example and test schema regenerates its `^OPCUA.DataSource` spec. Against `plc`: `MeasurementMetadataTest` 224/0, `PortalPipelineTest` 38/0, `ResolverTest` 78/0.
7. ✅ ~~**Subscriptions are never really deleted**~~ **Resolved 2026-10-21: no leak; misleading code removed** ✔ (`TCPSubscriptionInboundAdapter.cls:410`, `:453`). The adapter cleans up with `ReadBulkClear`, the polling API. Each reconnect probably leaks a subscription. Caveat: the tests note that the real `DeleteSubscriptionSet` double-frees memory in C++, so the root fix is in the native library. **Finding:** there is no leak. `ReadBulkClear` on a subscription handle does nothing (it looks in the polling map), but `Disconnect` already cleans up. open62541 1.2.1 closes the session with `deleteSubscriptions = true` (`ua_client_connect.c:1175`), and the client-side `Subscription` object is freed on the next `SetupClient` reset or when the client is closed. Measured against `plc`: 10 reconnect cycles gave 6 subscriptions created and 6 deleted on the server, and the client map stayed at one entry. A reconnect without a reset is refused ("Client reset required"), so nothing can pile up that way. **Fix:** removed the no-op `ReadBulkClear(subscriptionHandle)` calls (the reconnect path, and the `OnTearDown` override, which now falls back to `Common.OnTearDown`'s disconnect), and the same call in `MeasurementMetadataTest`'s teardown. `Client.DeleteSubscriptionSet` now documents why not to call it. Verified on IRIS 2025.3: `OPCUA` and `Examples` compile clean and `MeasurementMetadataTest` passes 224/0. A live subscription pipeline on `plc` stored 10 rows in 10 s, and stopping the production made the server log "Deleted the Subscription", with no warnings or errors on the item. **Native library fixed 2026-10-21 (closed-source `opc-ua-master`, commit `8dd71c5` in the local `cpp-build` repository; rebuilt for linux-amd64, linux-arm64 and windows-x64):** `OpcuaClient::deleteSubscription` freed the `Subscription` but left it in `m_subscription_map`, so `clear()` freed it again on the next reset or client close. That's the double free, and it killed the IRIS process with signal 11 (reproduced). It now removes the map entry first. It also marks the subscription `DEACTIVATED` before the server delete, so the delete callback no longer forces a client reset, and `SERVER_DELETED` after it, so the destructor doesn't send a second delete. `Subscription::deleteOnServer` read `results[0]` without checking it, a NULL dereference when the request itself fails. It now checks `serviceResult` and `resultsSize`, as open62541's own `deleteSingle` does, and clears the response, which used to leak. Verified with the new arm64 build installed in `iris-demo`: 3 create/delete/close cycles survive (the old build died on the first), the server logs every subscription deleted, and a new subscription after a delete polls without a reset. Suites against `plc`: `MeasurementMetadataTest` 227/0 (3 new delete checks), `PortalPipelineTest` 38/0, `ResolverTest` 78/0. A live subscription pipeline stores rows and its subscription is deleted on stop. The amd64 and Windows builds come from the same sources and compiled clean, but were not run: there is no IRIS for those platforms here. Only the wrapper binaries changed. `libopen62541`, `open62541.dll` and `libcrypto` are the files already shipped.
8. ✅ ~~**A batch's result depends only on its last notification**~~ **Fixed 2026-10-23** (`TCPSubscriptionInboundAdapter.cls:278-297`). If only the last notification fails, the whole successful batch takes the error path. If an earlier one fails, it is only counted. **Fix:** the loop moved into the new `ProcessBatch` method, which keeps each notification's status to itself and returns only the processed count, the error count and the first error. It returns no status, so `OnTask`'s `tSC` now only carries connection and poll failures. A failed notification is handled the same wherever it sits in the batch: it's counted, and the batch logs one warning that now includes the first error's text. A notification that throws is also caught and counted, so it no longer goes down the connection-error path. Only failures from `CheckInput` or `BuildRow` reach this loop, because the service already logs and skips a failed save. Polling isn't affected: it hands over one input per cycle. Added `MeasurementMetadataTest.TestSubscriptionBatch`, which drives `ProcessBatch` offline with the new `OPCUA.Tests.FakeBatchHost` for a failure in last place, in first place, two failures, a throw, and a clean batch. Verified on IRIS 2025.3 (`iris-opcua-iris-1`): `OPCUA`, `Examples` and the tests compile clean. Against `plc`: `MeasurementMetadataTest` 257/0, `PortalPipelineTest` 38/0, `ResolverTest` 78/0. A live `SubscriptionExample` connected, subscribed and stored records with no warnings or errors.
9. ✅ ~~**Pipelines stop for good after a 10-minute outage**~~ **Fixed 2026-10-23** (`TCPPollingInboundAdapter.cls:183`). With the defaults, a PLC down for more than 10 minutes stops collection until someone restarts the pipeline. The warning branch meant for `AlwaysConnect=1` can never run. **Fix:** `AlwaysConnect` now defaults to 1 in `Common`. Also fixed the "conection" typo in that warning in both adapters, and updated `docs/architecture.md`. Each timeout also logs the connect error once, because `OnTask` returns it. This was already true for the subscription adapter. Verified on IRIS 2025.3 (`iris-opcua-iris-1`): `OPCUA`, `Examples` and the tests compile clean. `PollingExample` ran against `plc` with `ConnectionRetryTimeout=10`, and `plc` was stopped for 40 s. 10. ✅ ~~**Production edits are not locked**~~ **Fixed 2026-10-29** (DeployService, PipelineService). Two requests at once, or a request plus a Portal edit, means the last save wins and the other change is silently lost. Rebind also saves in two separate steps. **Finding (IRIS 2025.3):** a stale save is silent on both sides. Copy A was opened, a separate process saved item X the way the Portal does (fresh open, item `%Save`, `SaveToClass(item)`), and then A saved. A's `%Save` left X's newer row alone, but A's `SaveToClass` wrote A's stale X into the class XData. Storage and class then disagreed, and `LoadFromClass` (run on every compile of the production class) lost the newer change. `Ens.Config.Production` and `Ens.Config.Item` have no `VERSIONPROPERTY` and store no change marker. The production class's `%Dictionary.ClassDefinition.TimeChanged` is a reliable stamp: every `SaveToClass` moves it, even an unchanged one, with sub-millisecond resolution, and the Portal always calls `SaveToClass`. The Portal locks with IRIS's deployment token (`Ens.Deployment.Token` "DeployToken"), not anything of ours, and its save deliberately checks no timestamp. In one process, `%OpenId(id, 0)` returns an already-open object unchanged, so "open fresh" needs `%Reload`. The user chose to use our own lock plus the stamp, with documented APIs only, and not the deployment token. **Fix:** the new `OPCUA.REST.ProductionEdit` handles every console read-modify-save:
    - `Begin` takes `^OPCUA.ProductionEdit` with a 10 s timeout. A busy lock fails with "Another change to the pipelines is in progress; try again."
    - `Begin` records `TimeChanged`, then opens the production and `%Reload`s it and its items.
    - `Commit` refuses with "The pipeline production was changed by someone else (for example in the Management Portal); reload and try again." when the stamp moved. Otherwise it runs `%Save` and `SaveToClass`, checking both.
    - `UpdateItem` applies settings (inserting missing ones) and item fields in one save.

    The routing:
    - Deploy (`AddServiceItem`, which rechecks the duplicate name under the lock), `Toggle`, `Delete` and `Rebind` all go through it.
    - Rebind changes devices and categories with one `UpdateItem`. `UpdateDeviceNodePaths`, `UpdateCategories` and `UpdateItemField` are gone.
    - Items are matched by exact name, so names with dots, spaces and hyphens work.
    - `Delete` no longer calls `EnableConfigItem` first. That method saves the production itself, outside the edit. Removing the item and then running `UpdateProduction` stops its job (checked: its `^Ens.Runtime` entry is gone).

    The new `ProductionEdit.ApplyToRunning` handles restart reporting:
    - `restarted` is 1 only when `UpdateProduction` returned OK.
    - A production that isn't running gives `restarted: 0` and a `restartNote`.
    - A suspended or troubled production, or a failed update, makes rebind fail with "Device list saved, but the running pipeline could not be restarted: …", and toggle and delete with similar "… saved, but …" text. The save is not rolled back.

    **Known limits** (also in `ProductionEdit` and `docs/architecture.md`):
    1. A Portal save that lands in the millisecond window between `Commit`'s stamp check and its `SaveToClass` is still overwritten in the class.
    2. A Portal page loaded before a console edit and saved after it overwrites the console's change. That is the Portal's own code, so it can't be closed from our side.

    **Verified** on IRIS 2025.3 (`iris-opcua-iris-1`):
    - `OPCUA`, `Examples` and the tests compile clean.
    - New offline `OPCUA.Tests.Unit.ProductionEditTest` (`TestLockBusy`, `TestStaleCommitRefused`, `TestUpdateItemOneSave` counting `SaveToClass` calls, `TestNamesWithPunctuation` on `Line 3.Press-A`): all four failed on the old code (no `ProductionEdit`) and pass now.
    - New live `OPCUA.Tests.Live.PipelineConcurrencyTest`: `TestParallelRebinds` runs three rounds of two `JOB`bed rebinds and checks that storage and class agree on one of the two lists. It passed on the old code too, because the old window is too short to hit reliably, so it is a regression guard. The deterministic proof is `TestStaleCommitRefused`. `TestRebindWhenProductionNotRunning` failed on the old code (no note, troubled returned OK) and passes now. Troubled can't be forced without faking Ensemble's runtime globals, so it comes from the process-private seam `^||OPCUA.Tests("productionStatus")`.
    - Suites: `Runner.Offline()` 37/0, `Runner.Live()` 35/0. Against `plc`: `MeasurementMetadataTest` 257/0, `PortalPipelineTest` 38/0, `ResolverTest` 78/0.
11. **Schema delete can miss a schema that is still in use** (`SchemaService.cls:698`). `MapSchemaUsage` swallows every error and only looks at `OPCUA.Pipeline.Production`. If it fails, or a pipeline lives in a hand-built production, the delete goes ahead.
12. **A failed schema creation leaves debris** (`SchemaService.cls:377-444`). Half-created serial or main classes stay behind, and every retry then fails with "already exists".
13. **String columns are capped at 50 characters** ✔ (`Types/StringDataValue.cls` and siblings). `%String` defaults to `MAXLEN=50`. Rows save today only because `SaveSourcedData` writes the global directly. A SQL UPDATE or `%Save` on a longer value fails, and SQL clients see VARCHAR(50).
14. **The status column is the wrong size** (plausible). `Status As %Integer` holds unsigned 32-bit codes, and every Bad code is above the INTEGER range. JDBC or ODBC `getInt` would likely overflow on exactly the readings you care about.
15. **OPC UA passwords are stored in plain text** in the production settings, and so in the production class source. Ens Credentials would avoid this.
16. **Wrong passwords return 404, not 401** ✔ (`Handler.cls:20`). The `Login()` override suppresses the login challenge. No data leaks, but it is confusing.
17. **The installer can't resume an interrupted namespace creation** (`ClientInstaller.cls:216-223`). If enabling interoperability fails, every rerun calls the namespace "in use by something else".
18. **The demo Docker build ignores compile failures** (`demo/iris/IRISConfig/Installer.cls:44-50`). A broken `backend/src` still produces a "successful" image.
19. ✅ ~~**Deleting a pipeline leaves its config item row behind**~~ **Fixed 2026-10-29** (found 2026-10-21 while fixing #7; `PipelineService.cls:365`, also `PortalPipelineTest.Cleanup`). `Items.RemoveAt` only takes the item out of the production's list. Its `Ens.Config.Item` row stays, still marked with the production and with its old `Enabled`. `FindItemByConfigName` looks items up by SQL and prefers an enabled row, so after deleting an enabled pipeline and creating a new one with the same name, it finds the orphan, which isn't in the list, and `Toggle` fails with "Pipeline '…' not found". Reproduced on `iris-demo`. **Fix:** `PipelineService.Delete` now captures the config item ID before `RemoveAt`, then calls `##class(Ens.Config.Item).%DeleteId(tItemId)` after `SaveToClass`. Same fix in `PortalPipelineTest.Cleanup` (with a Try/Catch per ID since cleanup should not fail). **Verified:** `OPCUA.Tests.Live.PipelineLifecycleTest.TestDeleteThenRecreateSameName` (9 assertions) deploys a pipeline, enables it, deletes it, asserts the config item row count is 0, redeploys with the same name, and toggles it - all pass. Regression gate: `MeasurementMetadataTest` 257/0, `PortalPipelineTest` 38/0, `ResolverTest` 78/0. Live suite: 9/0.

## AI-style patterns to watch

- **Code that throws a status as a "goto"** (`CreateFromStatus(0)`), instead of building a real status.
- **Swallowing errors as `$$$OK`** in helpers (`MapSchemaUsage`, `SafeReadValue`), a Python-style "best effort" habit. In this code it disables safety checks.
- **Assuming lists are always complete:** `$LI` where `$ListGet` is needed, and the last-status-wins logic in batches.
- **Pattern tests that are too loose:** `?1.N` on `$Piece` also matches when there is no delimiter at all.
- **Defaults never checked against this IRIS version:** the 29000 code, `MAXLEN=50`, delete without the `e` flag, and `HandleCorsRequest` (it does nothing because the CORS allowlist is empty ✔).

## Already done well

- **Consistent `Client.cls` wrapper:** every native call goes through Try/Catch, converts errors to statuses, has a single exit, and checks the return before reading the list.
- **Clean architecture:** one row-assembly implementation (`RowWriter`) and one resolve path shared by both adapters, so polling and subscriptions can't drift.
- **Load-bearing ordering is respected:** adapters drop the session when resolving fails (`TCPPollingInboundAdapter.cls:103`), so they retry instead of polling a dead handle.
- **Defensive code in the core:** `$IsObject` follows every `%OpenId` in Resolver and RowWriter, list positions come from compiled storage rather than guesses, and Bad readings are read safely.
- **Careful input parsing:** `ParseDeviceNodePaths` handles CRLF, comments and per-line errors.
- **Safe schema deletion targets:** `RequireSchema`/`IsSchema` stop arbitrary classes being deleted through the API ✔.
- **Type inference from metadata:** types come from DataType + ValueRank, and the probe is always cleared.
- **The ServerTS-free type family** is properly separate, not a subclass.
- **ClientInstaller:** uses the `Config`/`Security` class APIs (not SQL), checks hashes, never overwrites files it doesn't own, and writes no secrets to logs. The live web app, role and resource settings match the code ✔.
- **`MeasurementMetadataTest`:** thorough offline coverage of RowWriter.

## Test suite

- **Not standard and not CI-ready:** the tests are hand-written `Run()` harnesses, not `%UnitTest.TestCase` classes. They all need the docker `plc` server, and `PortalPipelineTest` relies on about 44 seconds of fixed `hang` waits.
- **Tests that pass when they shouldn't:**
  - `DataTest` returns success even when checks fail.
  - `TypeInferenceTest` counts "certified-server unreachable" as a pass.
- **Resolver and Portal tests only cover the old shape:** they use plain-column schemas. The shipping DataValue schema is never tested end to end through the Portal path.
- **Untested:**
  - the whole REST layer: rebind, toggle, delete, health, and delete-refusal
  - `ParseNodePath` edge cases
  - RowWriter with short input
  - subscription batches with more than one notification (offline coverage of `ProcessBatch` added with #8; the whole `OnTask` is still untested)

## Suggested order

1. Items 1–5: each is a small, low-risk change and fixes the most visible failures.
2. Items 10–12: locking and cleanup around production and schema edits. This is the bigger design fix.
3. Test suite: move the offline checks into `%UnitTest.TestCase` classes so they can run in CI without the docker servers.

## How this was checked

Four reviewers each read one area in full (client and types, adapters and data
model, REST, tests and installer). The main findings were then checked again in the
code and on `iris-demo`. The compose stack (with `plc`) was not running, so nothing
was tested against a live PLC.
