# ObjectScript repository audit

**Date:** 2026-10-15 · **Applies to:** `main` at `1346bbc` (release `setup-cli-v0.2.0`) · **IRIS used for checks:** `iris-demo`, IRIS 2025.3, namespace `OPCUA`

Items marked ✔ were checked against the running IRIS instance or confirmed in the
code by hand. Everything else comes from reading the code; "plausible" means likely
but not reproduced. No code was changed as part of this audit.

Items marked ✅ have since been fixed; each one notes the fix and how it was verified.

## Summary

The code is in better shape than most AI-generated ObjectScript. The classic syntax
traps are absent: no `$Get(obj.prop)`, no `Quit value` inside loops or Try blocks,
no bad postfix spacing, no transaction misuse.

The real problems are subtler. They are in error codes, edge cases around lists and
names, and how the code affects other things on the IRIS server (other productions,
leftover data).

5. ✅ ~~**One short result list kills a whole poll cycle**~~ **Fixed 2026-10-21** ✔ (`RowWriter.cls:173`). `$LI(pInput, i)` throws `<NULL VALUE>` when an element is missing. 7. ✅ ~~**Subscriptions are never really deleted**~~ **Resolved 2026-10-21: no leak; misleading code removed** ✔ (`TCPSubscriptionInboundAdapter.cls:410`, `:453`). The adapter cleans up with `ReadBulkClear`, the polling API. Each reconnect probably leaks a subscription. Caveat: the tests note that the real `DeleteSubscriptionSet` double-frees memory in C++, so the root fix is in the native library. **Finding:** there is no leak. `ReadBulkClear` on a subscription handle does nothing (it looks in the polling map), but `Disconnect` already cleans up. open62541 1.2.1 closes the session with `deleteSubscriptions = true` (`ua_client_connect.c:1175`), and the client-side `Subscription` object is freed on the next `SetupClient` reset or when the client is closed. Measured against `plc`: 10 reconnect cycles gave 6 subscriptions created and 6 deleted on the server, and the client map stayed at one entry. A reconnect without a reset is refused ("Client reset required"), so nothing can pile up that way. **Fix:** removed the no-op `ReadBulkClear(subscriptionHandle)` calls (the reconnect path, and the `OnTearDown` override, which now falls back to `Common.OnTearDown`'s disconnect), and the same call in `MeasurementMetadataTest`'s teardown. `Client.DeleteSubscriptionSet` now documents why not to call it. Verified on IRIS 2025.3: `OPCUA` and `Examples` compile clean and `MeasurementMetadataTest` passes 224/0. A live subscription pipeline on `plc` stored 10 rows in 10 s, and stopping the production made the server log "Deleted the Subscription", with no warnings or errors on the item. **Native library fixed 2026-10-21 (closed-source `opc-ua-master`, commit `8dd71c5` in the local `cpp-build` repository; rebuilt for linux-amd64, linux-arm64 and windows-x64):** `OpcuaClient::deleteSubscription` freed the `Subscription` but left it in `m_subscription_map`, so `clear()` freed it again on the next reset or client close. That's the double free, and it killed the IRIS process with signal 11 (reproduced). It now removes the map entry first. It also marks the subscription `DEACTIVATED` before the server delete, so the delete callback no longer forces a client reset, and `SERVER_DELETED` after it, so the destructor doesn't send a second delete. `Subscription::deleteOnServer` read `results[0]` without checking it, a NULL dereference when the request itself fails. It now checks `serviceResult` and `resultsSize`, as open62541's own `deleteSingle` does, and clears the response, which used to leak. Verified with the new arm64 build installed in `iris-demo`: 3 create/delete/close cycles survive (the old build died on the first), the server logs every subscription deleted, and a new subscription after a delete polls without a reset. Suites against `plc`: `MeasurementMetadataTest` 227/0 (3 new delete checks), `PortalPipelineTest` 38/0, `ResolverTest` 78/0. A live subscription pipeline stores rows and its subscription is deleted on stop. The amd64 and Windows builds come from the same sources and compiled clean, but were not run: there is no IRIS for those platforms here. Only the wrapper binaries changed. `libopen62541`, `open62541.dll` and `libcrypto` are the files already shipped.

10. ✅ ~~**Production edits are not locked**~~ **Fixed 2026-10-29** (DeployService, PipelineService). Two requests at once, or a request plus a Portal edit, means the last save wins and the other change is silently lost. Rebind also saves in two separate steps. **Finding (IRIS 2025.3):** a stale save is silent on both sides. Copy A was opened, a separate process saved item X the way the Portal does (fresh open, item `%Save`, `SaveToClass(item)`), and then A saved. A's `%Save` left X's newer row alone, but A's `SaveToClass` wrote A's stale X into the class XData. Storage and class then disagreed, and `LoadFromClass` (run on every compile of the production class) lost the newer change. `Ens.Config.Production` and `Ens.Config.Item` have no `VERSIONPROPERTY` and store no change marker. The production class's `%Dictionary.ClassDefinition.TimeChanged` is a reliable stamp: every `SaveToClass` moves it, even an unchanged one, with sub-millisecond resolution, and the Portal always calls `SaveToClass`. The Portal locks with IRIS's deployment token (`Ens.Deployment.Token` "DeployToken"), not anything of ours, and its save deliberately checks no timestamp. In one process, `%OpenId(id, 0)` returns an already-open object unchanged, so "open fresh" needs `%Reload`. The user chose to use our own lock plus the stamp, with documented APIs only, and not the deployment token. **Fix:** the new `OPCUA.REST.ProductionEdit` handles every console read-modify-save:
    - `Begin` takes `^OPCUA.ProductionEdit` with a 10 s timeout. A busy lock fails with "Another change to the pipelines is in progress; try again."
    - `Begin` records `TimeChanged`, then opens the production and `%Reload`s it and its items.
    - `Commit` refuses with "The pipeline production was changed by someone else (for example in the Management Portal); reload and try again." when the stamp moved. Otherwise it runs `%Save` and `SaveToClass`, checking both.
    - `UpdateItem` applies settings (inserting missing ones) and item fields in one save.

    The routing:
    - Deploy (`AddServiceItem`, which rechecks the duplicate name under the lock), `Toggle`, `Delete` and `Rebind` all go through it.
    - Rebind changes devices and categories with one `UpdateItem`. `UpdateDeviceNodePaths`, `UpdateCategories` and `UpdateItemField` are gone.
    - Items are matched by exact name, so names with dots, spaces and hyphens work.
    - `Delete` no longer calls `EnableConfigItem` first. That method saves the production itself, outside the edit. Removing the item and then running `UpdateProduction` stops its job (checked: its `^Ens.Runtime` entry is gone).

    The new `ProductionEdit.ApplyToRunning` handles restart reporting:
    - `restarted` is 1 only when `UpdateProduction` returned OK.
    - A production that isn't running gives `restarted: 0` and a `restartNote`.
    - A suspended or troubled production, or a failed update, makes rebind fail with "Device list saved, but the running pipeline could not be restarted: …", and toggle and delete with similar "… saved, but …" text. The save is not rolled back.

    **Known limits** (also in `ProductionEdit` and `docs/architecture.md`):
    1. A Portal save that lands in the millisecond window between `Commit`'s stamp check and its `SaveToClass` is still overwritten in the class.
    2. A Portal page loaded before a console edit and saved after it overwrites the console's change. That is the Portal's own code, so it can't be closed from our side.
    3. `DeployService.EnsureProductionExists` creates the production class on the first deploy ever, and it runs outside the lock. Two simultaneous first deploys can race on creating the class. One of them then fails with an error, but no data is lost. Not fixed.

    **Verified** on IRIS 2025.3 (`iris-opcua-iris-1`):
    - `OPCUA`, `Examples` and the tests compile clean.
    - New offline `OPCUA.Tests.Unit.ProductionEditTest` (`TestLockBusy`, `TestStaleCommitRefused`, `TestUpdateItemOneSave` counting `SaveToClass` calls, `TestNamesWithPunctuation` on `Line 3.Press-A`): all four failed on the old code (no `ProductionEdit`) and pass now.
    - New live `OPCUA.Tests.Live.PipelineConcurrencyTest`: `TestParallelRebinds` runs three rounds of two `JOB`bed rebinds and checks that storage and class agree on one of the two lists. It passed on the old code too, because the old window is too short to hit reliably, so it is a regression guard. The deterministic proof is `TestStaleCommitRefused`. `TestRebindWhenProductionNotRunning` failed on the old code (no note, troubled returned OK) and passes now. Troubled can't be forced without faking Ensemble's runtime globals, so it comes from the process-private seam `^||OPCUA.Tests("productionStatus")`.
    - Suites: `Runner.Offline()` 37/0, `Runner.Live()` 35/0. Against `plc`: `MeasurementMetadataTest` 257/0, `PortalPipelineTest` 38/0, `ResolverTest` 78/0.

    **Fix round 1 (2026-10-29):**
    - `PipelineConcurrencyTest` gained three tests, each driven by the `productionStatus` seam:
      - Suspended, alongside Troubled, for rebind.
      - `TestToggleWhenProductionNotRunning` and `TestDeleteWhenProductionNotRunning`, which pin the "… saved, but …" and "Pipeline deleted, but …" texts.

14. ✅ ~~**The status column is the wrong size**~~ **Fixed 2026-10-29** (`Types/AbstractDataValue.cls:10`, `Types/NoServerTS/AbstractDataValue.cls:20`). 16. ✅ ~~**Wrong passwords return 404, not 401**~~ **Fixed 2026-10-29 in the console; IRIS still answers 404** (`Handler.cls` `Login`, `webapp/src/app/core/services/api.service.ts`). The audit blamed the `Login()` override. **Cause, traced with `^ISCLOG`:** after a failed sign-in, CSP calls the dispatch class's `Login` in the pre-login context, user `CSPSystem` with no roles. That context cannot read `%DB_OPCUA` (no public permission). Loading `OPCUA.REST.Handler` fails with `<PROTECT>`, and CSP answers a bare `404 Not Found` (text/html) itself. Neither the old override nor the new one ever runs. **Decision (user):** no IRIS security change. Granting `CSPSystem` or the public read on the code database was rejected. This overturns the spec's #16 "my call": the API cannot return 401 under the default setup. **Fix:**
    - `Login` now follows `%CSP.REST.Login` (CORS, OPTIONS) but answers 401 with `{"status":"error","error":"Sign-in failed"}` and no `WWW-Authenticate` header. It is kept for any setup where the pre-login context can read the code database, and its comment says why it does not run by default.
    - The console's `isSignInFailure()` treats a 401, or a 404 without our JSON envelope, as a failed sign-in. A real 404 from the API always carries the envelope (e.g. `GET /schemas/NoSuch`), so the two stay apart.
    - `apiErrorMessage()` shows "Sign-in failed" for these. In the hosted console, Settings opens on the sign-in tab with that notice, without a browser pop-up. After the user dismisses it, background calls don't reopen it until the account changes.
    - **curl and other API clients still see IRIS's bare 404** for a wrong password.

## AI-style patterns to watch

- **Code that throws a status as a "goto"** (`CreateFromStatus(0)`), instead of building a real status.
- **Swallowing errors as `$$$OK`** in helpers (`MapSchemaUsage`, `SafeReadValue`), a Python-style "best effort" habit. In this code it disables safety checks.
- **Assuming lists are always complete:** `$LI` where `$ListGet` is needed, and the last-status-wins logic in batches.
- **Pattern tests that are too loose:** `?1.N` on `$Piece` also matches when there is no delimiter at all.
- **Defaults never checked against this IRIS version:** the 29000 code, `MAXLEN=50`, delete without the `e` flag, and `HandleCorsRequest` (it does nothing because the CORS allowlist is empty ✔).

## Already done well

- **Consistent `Client.cls` wrapper:** every native call goes through Try/Catch, converts errors to statuses, has a single exit, and checks the return before reading the list.
- **Clean architecture:** one row-assembly implementation (`RowWriter`) and one resolve path shared by both adapters, so polling and subscriptions can't drift.
- **Load-bearing ordering is respected:** adapters drop the session when resolving fails (`TCPPollingInboundAdapter.cls:103`), so they retry instead of polling a dead handle.
- **Defensive code in the core:** `$IsObject` follows every `%OpenId` in Resolver and RowWriter, list positions come from compiled storage rather than guesses, and Bad readings are read safely.
- **Careful input parsing:** `ParseDeviceNodePaths` handles CRLF, comments and per-line errors.
- **Safe schema deletion targets:** `RequireSchema`/`IsSchema` stop arbitrary classes being deleted through the API ✔.
- **Type inference from metadata:** types come from DataType + ValueRank, and the probe is always cleared.
- **The ServerTS-free type family** is properly separate, not a subclass.
- **ClientInstaller:** uses the `Config`/`Security` class APIs (not SQL), checks hashes, never overwrites files it doesn't own, and writes no secrets to logs. The live web app, role and resource settings match the code ✔.
- **`MeasurementMetadataTest`:** thorough offline coverage of RowWriter.

## Test suite

- **Not standard and not CI-ready:** the tests are hand-written `Run()` harnesses, not `%UnitTest.TestCase` classes. They all need the docker `plc` server, and `PortalPipelineTest` relies on about 44 seconds of fixed `hang` waits.
- **Tests that pass when they shouldn't:**
  - `DataTest` returns success even when checks fail.
  - `TypeInferenceTest` counts "certified-server unreachable" as a pass.
- **Resolver and Portal tests only cover the old shape:** they use plain-column schemas. The shipping DataValue schema is never tested end to end through the Portal path.
- **Untested:**
  - the whole REST layer: rebind, toggle, delete, health, and delete-refusal
  - `ParseNodePath` edge cases
  - RowWriter with short input
  - subscription batches with more than one notification (offline coverage of `ProcessBatch` added with #8; the whole `OnTask` is still untested)

## Suggested order

1. Items 1–5: each is a small, low-risk change and fixes the most visible failures.
2. Items 10–12: locking and cleanup around production and schema edits. This is the bigger design fix.
3. Test suite: move the offline checks into `%UnitTest.TestCase` classes so they can run in CI without the docker servers.
